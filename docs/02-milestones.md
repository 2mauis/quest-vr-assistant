## 首要关口与执行顺序

仓库整理已先提交并推送为 `a63a725`，随后继续阶段 1。用户后续明确授权隔离源码适配、专用具名 Tunnel / DNS、限时管理凭据，以及路由器针对 cloudflared 的 fake-IP 排除规则。健康探针始终与现有 MCP、显示、配对和私有服务隔离；没有安装第三方 App、配置自启、修改设备权限 / 睡眠 / 系统 DNS / 信任或关闭 TLS 校验。

首次诊断确认 Linux 发布资产找不到预期 DNS 配置。后续构建通过进程解析器和内部 DNS 服务使用 Quest 当前网络已有 DNS，并通过环境变量读取 Android 现有 CA 目录。路由器排除规则生效后，实际 Quest 建立 4 条 QUIC 连接，Cloudflare 显示 healthy；外部 HTTPS 响应和设备端随机码回执一致。最终启动日志无 error / fatal 或内部 DNS 初始化错误。验证结束后撤下临时路由、停止并清理探针，保留已授权的专用 Tunnel、DNS 与本机私有凭据。详情见[验证记录](03-validation-baseline.md)。

用户随后明确选择继续验证 Quest App 内置 Tunnel。最小诊断 APK 已在 App UID 下完成公网回环与基本退出验证；测试后卸载，保留构建源码及本地 APK。未改动设备设置，未接入正式 MCP 或配置自启。详情见[最新实机记录](03-validation-baseline.md#quest-app-内置-tunnel最小诊断-apk)。

**不能合并的验收项：**二进制执行、出站隧道与外部健康回环、自动启动 / 失败恢复、自研 APK 内置、长时 / 休眠 / 网络切换。当前证据覆盖诊断 APK 的 App UID 和短时生命周期；不能把阶段 2 整体或后续阶段标为完成。

阶段 2 与 3 都是完整工作区的前置证据。遇到内置限制可以评估已经确认允许的后台辅助组件，但不能直接安装或启用它；遇到语音或共存限制先记录实际冲突。常在线服务端只在明确需求或实测限制下由用户再决定，不自行迁移 MCP 主位置。

当前网页登录 / 语音基础关口已由用户确认通过。阶段 1 的下一项是：网页语音经现有中继调用 `show_scene`、`render_panel`、`clear`，头显返回 `delivered: true`。把 MCP 迁入 APK、具名 Tunnel、重启后补发旧命令和回写 `pose` 都不阻塞这项。不再以第三方 Grok APK 的启动限制阻塞这条路线。
