## 已确定

- 新方案采用原生 Quest 应用，在同一透视 / MR 体验中组织空间面板与视觉联动；具体原生技术栈和 MCP 服务位置待选。本轮仅提交方案供需求核对，尚未授权实施。
- 已调通实现保存在独立归档中，验收与未完成项见[检查点记录](07-milestones.md)。
- 托管端通过自定义 MCP 连接器调用显示工具。本仓库不实现模型 API 客户端。
- 协议实现为 2026-07-28，并保留 2025-11-25 的初始化握手。
- MCP 鉴权是环境变量中的静态 Bearer。不实现 OAuth。
- 本地进程用两个 localhost 端口把 `/mcp` 和显示页分开。
- 公网中转的目标仍是 VPS、Caddy、Node 和 systemd。域名和秘密只写在私有配置里。
- 页面点击以 `interaction` 事件留在中继内，不向外部投递。

## 原生 MR 方案研究（待需求核对，2026-11-01）

原生方向已确定。新方案将自由摆放的空间面板、透视模式与现实视觉联动组织为同一个助手体验，不另做独立采集产品。详见[原生 MR 空间助手方案](08-native-spatial-options.md)。

技术栈优先候选为 Meta Spatial SDK + Compose；若系统独立窗口共存更重要，则比较普通 Android 多 Activity。常在线 MCP / 中继与 Quest 本机 MCP + Tunnel 分别评估，后台任务和 MR 视觉联动按不同生命周期验证。本轮未实施新方案，现有服务和 MCP 契约未改变；Tunnel 与历史否决的 Worker 方案不同。
